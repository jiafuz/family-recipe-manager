# 首版 MVP 范围与验收标准

## 1. 产品目标

首版只解决一个完整问题：家庭成员把“吃什么”变成一份共同可编辑的菜单，并自动得到需要采购的食材。

核心闭环：

```text
创建／加入家庭厨房
→ 收录或维护家庭菜谱
→ 选菜
→ 选择日期与餐次
→ 保存菜单
→ 查看点餐记录
→ 自动得到采购清单
→ 完成本餐
```

所有成员使用同一套界面，不区分掌勺人、普通成员、家庭餐桌或个人餐桌。

## 2. 首版必须上线

### 2.1 账号与家庭厨房

- 微信授权登录，生成独立系统用户 ID。
- 创建厨房、使用 6 位邀请码加入厨房。
- 查看厨房成员、邀请成员、退出厨房。
- 厨房创建者可以修改厨房资料和移除成员。
- 普通业务操作不区分成员角色，所有成员均可点菜、编辑未来菜单和维护家庭菜谱。

### 2.2 家庭菜谱

- 手动创建菜谱，维护封面、食材、用量、步骤、口味和分类。
- 从菜谱广场收录后生成独立家庭版本。
- 家庭菜谱支持版本记录、编辑和撤销最近一次修改。
- 菜谱可以设置为“开放点菜”或“想学先存”。
- 点菜页只展示当前厨房中开放点菜的菜谱。

### 2.3 点菜

- 普通点菜必须完成“选菜 → 选择日期餐次 → 提交订单”。
- 从点餐记录进入编辑时锁定日期餐次，不重复选择时间。
- 支持数量、单菜口味备注和整餐备注。
- 空菜单不得提交。
- 提交后立即生效，并精准跳转到相应日期和餐次的点餐记录。
- 每次保存记录修改人、修改时间和版本。

### 2.4 点餐记录

- 查看历史、今天和未来任意日期。
- 按早餐、午餐、晚餐查看菜单。
- 未来菜单可编辑；历史菜单只读并可以“再点一次”。
- 单道菜可以左滑删除，删除前二次确认。
- 完成本餐后关闭菜单编辑、删除和邀请厨师能力。

### 2.5 采购清单

- 菜单保存后实时派生采购清单，不增加确认或生成步骤。
- 按蔬菜、肉禽、水产蛋奶、主食、调味等分类聚合。
- 标注每项食材来自哪一餐、哪道菜。
- 食材默认标记为需要购买，取消勾选表示无需购买。
- 可以查看全天或某几餐的合并清单，并生成分享内容。

### 2.6 图片和分享

- 完成本餐不强制上传照片。
- 已完成餐次可添加、编辑、替换和删除成品照。
- 相册支持单选和多选；拍照一次添加一张。
- 有成品照后可以分享本餐到微信。
- 分享前允许隐藏家庭名称、上传成员等信息。

### 2.7 基础运营能力

- 家庭动态和 APP 通知。
- 用户注销、数据导出申请、隐私设置。
- 服务端日志、监控、告警和数据库备份。
- 最小管理能力：查询用户／厨房、处理举报、下架公开内容、封禁异常账号。

## 3. 首版暂缓

以下能力保留产品设计，但不阻塞首版上线：

- 分享广场的评论、关注和复杂互动。
- 精确热量或医学性质的营养结论。
- 机器学习推荐模型。
- 多日制作回忆的高级排版模板。
- 独立 APP、H5 完整版和其他小程序平台。
- 付费会员、广告、电商采购和配送。

分享广场可以在内测环境启用，但公开上线前必须同时具备内容审核、举报、删除、封禁和运营后台。

## 4. 核心验收场景

### 场景 A：新家庭完成首次点菜

1. 用户创建厨房并邀请一位成员。
2. 从菜谱广场收录三道菜并设置为开放点菜。
3. 两位成员先后为明日晚餐加菜。
4. 第二位成员能看到已有菜品、点餐人和点餐时间。
5. 保存后点餐记录和采购清单立即更新。

### 场景 B：菜单发生变化

1. 用户取消一道尚未制作的菜。
2. 删除操作二次确认。
3. 该菜独有食材从采购清单消失。
4. 与其他菜共享的食材只减少相应用量。
5. 已存在食材的采购勾选状态被保留。

### 场景 C：多人并发

1. 两位成员同时打开同一餐菜单。
2. 第一位先保存。
3. 第二位保存旧版本时收到冲突提示，不静默覆盖第一位的修改。
4. 用户刷新后可以重新合并并提交。

### 场景 D：完成和留影

1. 用户点击完成本餐，菜单进入只读状态。
2. 用户可以忽略成品照直接离开。
3. 任意成员之后都可补充多张照片。
4. 照片修改和删除同步反映到分享预览。

## 5. 首版成功指标

- 新家庭完成第一次点菜的比例。
- 从打开点菜到保存菜单的完成率和中位耗时。
- 已保存菜单成功生成采购清单的比例必须为 100%。
- 菜单更新与采购清单不一致的严重缺陷数必须为 0。
- 关键 API 成功率不低于 99.9%。
- 用户可以在不阅读帮助文档的情况下完成核心闭环。
