# 权限模型与数据边界

## 1. 基本原则

- 是否能访问家庭数据，取决于当前用户是否是该厨房的有效成员。
- 用户传入的 `kitchenId`、`userId` 和资源 ID 都不可信，后端必须重新查询归属关系。
- 普通点菜、菜单编辑、采购勾选和家庭菜谱维护不区分掌勺人或普通成员。
- `owner` 只用于管理厨房本身，不成为业务角色。
- 公开内容和家庭私密内容使用不同的数据访问路径。
- 管理后台账号与普通用户账号分开，所有管理动作记录审计日志。

## 2. 权限矩阵

| 操作               | 厨房成员 | 厨房创建者 | 平台运营     |
| ------------------ | -------- | ---------- | ------------ |
| 查看本厨房数据     | 是       | 是         | 仅经授权排障 |
| 点菜和编辑未来菜单 | 是       | 是         | 否           |
| 更新采购勾选       | 是       | 是         | 否           |
| 创建和编辑家庭菜谱 | 是       | 是         | 否           |
| 完成本餐、添加照片 | 是       | 是         | 否           |
| 邀请成员           | 是       | 是         | 否           |
| 修改厨房名称和头像 | 否       | 是         | 否           |
| 移除其他成员       | 否       | 是         | 否           |
| 转让厨房           | 否       | 是         | 否           |
| 解散厨房           | 否       | 是         | 否           |
| 发布公开内容       | 是       | 是         | 否           |
| 举报公开内容       | 是       | 是         | 否           |
| 下架违规公开内容   | 否       | 否         | 是           |
| 封禁异常账号       | 否       | 否         | 是           |

“所有家庭成员功能一致”不等于所有人都可以解散家庭或移除其他成员。厨房管理属于安全边界，不属于点菜角色。

## 3. 菜单状态规则

### planned

- 今天或未来的菜单可以编辑。
- 所有成员可以新增、修改、删除菜品。
- 支持邀请厨师。
- 修改必须携带当前版本号。

### completed

- 菜单和菜品只读。
- 不允许左滑删除、编辑菜单或邀请厨师。
- 允许任意成员继续添加、编辑和删除成品照。
- 如需纠正误完成状态，首版只允许从修改历史执行明确的“恢复为计划中”，并记录审计。

### 历史未完成异常

- 日期早于今天但仍是 planned 时，界面提示“未标记完成”。
- 允许成员补记完成，不能直接修改过去的菜单。

## 4. 资源访问检查

每个家庭资源请求必须执行：

1. 验证会话有效。
2. 根据资源 ID 查询真实 `kitchen_id`。
3. 验证当前用户存在有效 `kitchen_members` 记录。
4. 验证资源状态、日期和操作类型。
5. 记录写操作的操作者、请求 ID 和结果。

禁止仅通过“URL 中的厨房 ID 等于当前厨房 ID”来授权。

## 5. 文件访问

- 家庭成品照默认私有。
- API 验证成员身份后签发短期读取地址。
- 分享到微信时生成新的脱敏分享图，不把私有原图永久公开。
- 发布到分享广场后，为公开帖子生成单独的公开派生资源。
- 删除照片时先软删除数据库关联，异步清理无引用文件。

## 6. 邀请安全

- 邀请码有效期默认 7 天。
- 明文邀请码只在创建时返回一次。
- 限制单个用户和 IP 的尝试频率。
- 连续失败触发短期冷却。
- 加入前向用户展示厨房名称和成员数量并要求确认。
- 达到成员上限、已撤销或已过期时统一返回不可加入，避免泄露更多信息。

## 7. 运营权限

管理后台至少分为：

- support：只读查询脱敏账号状态。
- moderator：处理公开内容、举报和封禁。
- administrator：配置运营账号和高风险操作。

查看家庭私密菜单或照片必须有明确工单理由并产生审计记录。生产数据库不允许日常人工直接修改。
