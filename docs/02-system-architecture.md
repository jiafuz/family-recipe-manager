# 系统架构设计

## 1. 架构决策

### ADR-001：Taro + React + TypeScript

首发平台是微信小程序，但未来可能扩展 H5 或独立 APP。Taro 提供多端编译能力，React 与 TypeScript 便于组件化、测试和共享数据契约。

现有 `index.html` 只作为产品原型，不直接作为正式前端运行时。

### ADR-002：模块化单体后端

首版使用一个可独立部署的 API 服务，按业务拆分模块，不拆微服务：

- auth：登录与会话
- kitchens：厨房、成员与邀请
- recipes：公共菜谱、家庭版本与版本历史
- mealPlans：点菜、菜单和修改历史
- procurement：采购清单派生
- media：上传、照片和缩略图
- discovery：菜谱广场、分享广场与举报
- notifications：家庭动态和 APP 通知
- recommendations：今日推荐
- users：个人资料、导出与注销

当单个模块有独立扩缩容、独立故障域或独立发布需求时，才考虑拆服务。

### ADR-003：MySQL 是业务事实库

家庭成员、版本、菜单、食材来源和权限具有明确关系，并需要事务和约束，因此使用 MySQL。图片文件不进入数据库。

### ADR-004：菜单是采购清单的唯一来源

采购清单不能独立创建或手工维护食材名称和用量。它由当前菜单版本中的菜谱食材实时派生，只额外保存用户的“是否需要购买”选择。

### ADR-005：客户端只通过 API 执行业务写操作

客户端可以直接上传文件到受限的对象存储临时地址，但菜单、成员、菜谱、分享和权限相关写操作全部进入后端。后端负责成员身份、数据范围、版本冲突和事务。

## 2. 逻辑架构

```text
微信小程序 / 未来 H5 / 管理后台
                 │ HTTPS + JSON
                 ▼
       CloudBase 网关或云托管
                 │
                 ▼
        Fastify 模块化 API
     ┌───────────┼───────────┐
     ▼           ▼           ▼
  MySQL       对象存储      异步任务
  业务数据     图片/分享图    缩略图/通知/审核
```

## 3. 部署单元

### 小程序

- 编译产物上传微信开发者工具。
- 请求域名只允许生产 API 域名。
- 环境变量只保存公开配置，不保存数据库密钥或管理密钥。

### API

- 以容器形式部署至 CloudBase 云托管。
- 提供 `/health/live` 和 `/health/ready`。
- 无状态运行，可以水平扩容。
- 登录态使用短期访问令牌和可撤销的刷新会话。

### MySQL

- 开启自动备份和时间点恢复能力。
- 数据库变更只能通过版本化迁移执行。
- 生产账号按最小权限配置，不使用管理员账号运行应用。

### 文件存储

- 客户端先向 API 申请短期上传凭证。
- 上传后由异步任务执行格式校验、去除 EXIF、生成缩略图和内容安全检查。
- 私密家庭照片默认使用私有读权限，通过短期签名 URL 访问。

## 4. 关键业务数据流

### 保存菜单

1. 客户端提交目标日期、餐次、菜单版本、菜品和幂等键。
2. 后端验证当前用户属于目标厨房。
3. 事务内锁定菜单，比较版本号。
4. 保存菜单新版本和修改日志。
5. 根据菜谱版本重新计算食材汇总。
6. 保留仍存在食材的采购勾选状态；新增食材默认勾选。
7. 提交事务并发布“菜单已更新”领域事件。
8. 异步生成家庭通知和埋点。

### 上传成品照

1. 客户端申请上传凭证。
2. 客户端压缩后直传对象存储。
3. API 创建待处理媒体记录。
4. 异步任务生成缩略图并执行安全检查。
5. 通过后照片才可以公开发布到分享广场。

## 5. 多环境

必须建立互相隔离的环境：

| 环境       | 用途                   | 数据                    |
| ---------- | ---------------------- | ----------------------- |
| local      | 本地开发               | 本地 MySQL 或开发数据库 |
| test       | 自动测试、联调         | 可随时重建的测试数据    |
| staging    | 小范围体验版、上线验收 | 脱敏或专用体验数据      |
| production | 正式用户               | 严格权限和备份          |

任何环境都不能共享数据库、对象存储桶、密钥或微信回调配置。

## 6. 性能和可用性目标

- 核心读取接口 P95 响应时间目标：500 毫秒以内，不包含图片下载。
- 核心写入接口 P95 响应时间目标：800 毫秒以内。
- 月度核心 API 可用性目标：99.9%。
- 列表接口必须分页，默认 20 条，禁止无上限读取。
- 所有高频查询建立复合索引并通过执行计划验证。
- 分享图、缩略图、通知和内容审核放入异步任务，不阻塞菜单保存。

首版不引入 Kubernetes、服务网格和分布式事务。达到明确瓶颈前，不为假设中的超大规模增加复杂度。

## 7. 演进路线

### 阶段一：0—1 万活跃用户

- 单 API 服务多实例。
- 单 MySQL 主库。
- CloudBase 文件存储。
- 应用内任务表或托管队列。

### 阶段二：查询或任务出现瓶颈

- 引入 Redis 缓存公开菜谱和推荐结果。
- 图片处理、通知、分享图拆为独立工作进程。
- 建立只读副本支持运营分析。

### 阶段三：单模块需要独立扩展

- 优先拆分媒体、通知、搜索和推荐。
- 菜单与采购保持在同一事务边界内，不轻易拆开。
