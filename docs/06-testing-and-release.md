# 测试、发布与运维方案

## 1. 测试分层

### 单元测试

优先覆盖不依赖网络的核心规则：

- 菜单食材聚合。
- 单位和食材标准化。
- 菜单变化后采购勾选状态保留。
- 推荐规则打分。
- 日期、餐次和时区处理。
- 菜单状态机和权限判断。

### 集成测试

使用独立测试数据库验证：

- 微信身份映射和会话刷新。
- 创建／加入厨房。
- 菜谱版本和回退。
- 菜单事务、版本冲突和幂等提交。
- 采购清单重算。
- 文件元数据与业务关联。

每个测试独立准备和清理数据，禁止连接生产数据库。

### 端到端测试

至少覆盖：

1. 新用户创建厨房并完成首次点菜。
2. 成员通过邀请码加入并修改同一餐。
3. 从点餐记录编辑后返回原日期餐次。
4. 菜单删改同步采购清单。
5. 完成本餐后菜单只读、照片可继续添加。
6. 上传多张照片、替换、删除和分享预览。

### 人工验收

- 主流 iPhone 和 Android 设备。
- 小屏幕、大字号和安全区域。
- 弱网、断网和接口超时。
- 重复点击、快速切页和返回。
- 微信分享、相册、相机和隐私授权。

## 2. 持续集成

每次合并请求执行：

```text
安装锁定依赖
→ 格式检查
→ TypeScript 类型检查
→ 单元测试
→ API 集成测试
→ 小程序构建
→ 数据库迁移校验
→ 依赖和密钥扫描
```

失败不得合并。生产部署只允许从受保护的 `main` 分支和带版本标签的提交触发。

## 3. 发布流程

1. 功能在开发环境完成。
2. 合并到测试分支并自动部署测试环境。
3. 产品在 staging 小程序体验版验收。
4. 执行数据库备份和迁移预演。
5. 创建版本标签和发布说明。
6. 先部署兼容旧客户端的后端。
7. 提交微信小程序审核。
8. 通过后灰度或分阶段发布。
9. 观察错误率、响应时间和核心转化。

数据库采用“扩展—迁移—收缩”方式：先新增兼容字段，再迁移数据，确认旧版本停止使用后才删除旧字段。

## 4. 回滚

- 前端保留上一个审核通过版本。
- API 镜像保留最近稳定版本。
- 数据库迁移必须提供前滚修复方案；含数据变更的迁移不能假定简单回滚安全。
- 新功能使用服务端开关，可在不重新审核小程序的情况下关闭高风险入口。
- 发布后 30 分钟重点监控，严重故障立即停止灰度并回滚服务。

## 5. 可观测性

### 日志

- 使用结构化 JSON 日志。
- 包含 requestId、userId 脱敏值、kitchenId、路由、耗时、状态码。
- 禁止记录登录 code、访问令牌、OpenID、邀请码明文和照片地址签名。

### 指标

- 请求量、错误率、P50/P95/P99 延迟。
- MySQL 连接数、慢查询和事务冲突。
- 对象存储容量和下行流量。
- 异步任务积压、失败和重试次数。
- 登录、菜单保存、采购清单生成和分享成功率。

### 告警

- 5 分钟错误率超过阈值。
- 核心 API 连续不可用。
- 数据库连接或磁盘异常。
- 任务队列持续积压。
- 云费用或图片流量异常增长。

## 6. 备份和恢复

- MySQL 每日全量备份并开启时间点恢复。
- 每季度至少进行一次恢复演练。
- 关键配置、迁移和基础设施代码进入 Git。
- 对象存储开启版本控制或回收站策略。
- 明确定义：RPO 目标 24 小时以内，核心数据库争取缩短到 5—15 分钟；RTO 初期目标 4 小时以内。

没有经过恢复演练的备份不能视为可靠备份。

## 7. 上线前检查

- [ ] 核心验收场景全部通过。
- [ ] 没有高危安全漏洞和明文密钥。
- [ ] 数据库索引通过执行计划检查。
- [ ] 生产备份、告警和费用预算已开启。
- [ ] 隐私政策和实际代码收集行为一致。
- [ ] 用户注销、数据导出和举报链路可用。
- [ ] 内容安全服务和人工复核入口可用。
- [ ] 小程序备案、域名和主体资料完成。
- [ ] 发布与故障联系人明确。

## 8. 当前依赖安全基线

截至 2026-07-23，Taro 4.2.1 的上游依赖仍固定引用存在公开安全通告的旧版 `swiper`、`webpack`、`webpack-dev-server`、`esbuild` 和 `uuid`。这些依赖主要属于小程序／H5 编译工具链，但公开测试和正式发布前仍必须处理。

- 不执行会把 Taro 强制降级到不兼容版本的 `npm audit fix --force`。
- 持续关注 Taro 的兼容修复版本，升级后重新执行类型检查、小程序构建和完整回归。
- 如需临时覆盖上游依赖，必须同时验证微信小程序和未来 H5，不能只以 `npm audit` 数量下降作为验收标准。
- 在问题解决前，开发服务器只监听本机，不暴露到公共网络。
- 将“生产依赖无高危／严重漏洞”作为公开测试和正式上线的发布门槛。
